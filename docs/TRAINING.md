# Training Jev to solve the cube — our way

> The whole point: **the provider's dataset is irrelevant.** The cube is a perfect
> simulator that lives in this repo, so every example, every label, and every
> episode of "experience" is generated by *us*. Jev is not a move generator —
> it is a judgment function (`systemOne`: `choice` / `score` / `noul` over a
> state we provide). We train the *policy around* that judgment function using
> our own data, and the cube itself is the teacher.

## 1. What "solving" means for a judgment model

Verified constraint (see `src/server/jev-engine.ts`, `node_modules/jev-engine`):
the engine's only inference call answers structured questions about a state.
It cannot emit free-form moves, and the SDK has no fine-tuning endpoint.
Therefore:

- **The move generation is our toolbox** (`src/lib/solve-lbl.ts`, `src/lib/solve-kociemba.ts`).
- **Jev's trainable skill is the policy**: given full cube reality, which tool
  next? (`availableTools()` in `src/app/api/solve/route.ts` is the action space.)
- The agent loop in the route is the **episode runner**.

Formally this is a deterministic, fully observable MDP:

| RL concept | In rubikjev |
|---|---|
| State `s` | facelet string + cubie arrays + `progressOf()` summary |
| Action `a` | one single move out of the 18-move alphabet, judged every turn |
| Transition `T(s'|s,a)` | exact, local: the server executes the judged move |
| Reward `r(s,a)` | ours to design (§3) |
| Policy `π(a|s)` | Jev's `choice` over the offered options |

## 2. Free, perfect labels — the cube is the teacher

Because both solvers are deterministic and fast, at any state `s` we can
compute the ground-truth value of **every** candidate tool:

```text
for each scramble (self-generated, any length):
  s ← scrambled cube
  while s is not solved:
    for each tool a in availableTools(s):
      s' ← apply(a)          # local sim, microseconds
      v(s,a) ← Δsolved_pieces(s') / moves(a)   # progress per move spent
    label a* = argmax v(s,a)
    emit (facelets(s), progress(s), options, a*, v(s,·))  → dataset.jsonl
    s ← apply(a*)
```

This generates unlimited supervised episodes with **zero human labeling and
zero provider data**. The same generator labels the judgment rubric with exact
ground truth (`difficulty` from `scrambleStats()`, `genuine_chaos` from the
cancellation count), which calibrates the verdict side of Jev too.

Run it as: `scripts/training-data.mjs` (see §6), emit JSONL, keep it in-repo
or in a bucket — it is *our* dataset, reproducible from a seed.

## 3. Reward design

Shaped reward beats sparse "solved" for an 18-move alphabet:

```
r(s,a) = 10 · Δsolved_pieces(a)      # cross edges, corners, threads, LL jobs
       − 0.1 · moves(a)              # shorter is better
       − 1.0 · engine_calls(a)       # tokens/latency cost (speedrun = 1 call)
       + 50  · solved                # terminal bonus
```

Two structural notes:

- **`speedrun` is the anytime escape hatch.** It always finishes (Kociemba
  ≤22 moves) but hands the show to the tool — Jev must learn when invoking it
  is worth surrendering the spotlight.
- **GRIND vs SWIFT cross** is a pure style/efficiency fork — the label
  generator gives exact values for both, so Jev can learn when the human-way
  grind is "worth it" for the audience vs. strictly optimal.

## 4. Where the learned policy actually lives (no fine-tuning)

Three layers, all ours, in increasing strength:

### Layer 1 — context is training (ship today, zero infra)

Judgment models weight the state they're given. So "train" = curate what we
feed: a compact **playbook** block distilled from the generated dataset
("if ≥3 cross edges unsolved → cross first; a corner already above its slot →
seat it; ≤2 LL jobs left and budget tight → speedrun"), plus a handful of
best-pick exemplars (state-summary → tool) from `dataset.jsonl` inlined into
the `state` field of each call. This changes behavior with **our** examples —
it is in-context learning on our data, not the provider's.

### Layer 2 — own the value estimates (bandit on our episodes)

Log every pick the route makes: `(state features, options, Jev's pick, outcome)`
into a server-side store. Maintain per-tool mean reward conditioned on cheap
state features (phase flags from `progressOf()`). Use it two ways:

- **re-rank the option menu** before each call (Jev chooses among pre-ranked
  candidates — its judgment, our learning),
- **guardrail**: if Jev's pick underperforms the bandit's estimate badly,
  execute the bandit's choice instead (and count the override).

This learns continuously from live play, entirely in our infra.

### Layer 3 — Jev as value function (the real "Jev solves", move-level)

`noul` returns a probability — perfect for a learned **value function**.
DeepCubeA-style but judgment-powered:

1. Server expands candidate next-states (per tool, or even per move-batch).
2. Ask Jev: *"How close to solved is this state?"* → `noul` score per candidate.
3. Pick argmax, execute, verify locally, repeat.

Train this scorer **with our simulator**: include labeled exemplar states in
the call (state → known distance-to-solved, computed by Kociemba/optimal or by
pieces-solved heuristic), measure calibration against ground truth offline,
grow the exemplar set until the ranking is reliable. Then the search — our
code — can go move-granular with Jev paving every step. Cost: one engine call
per candidate per step, so it needs the budget gate; it is the frontier, not
the default.

## 5. Evaluation: fixed suite, three baselines

Freeze a seeded scramble suite (e.g. 100 seeds × lengths {10, 18, 25, 100}).
Track per variant of the policy:

- moves streamed, engine calls, tokens, wall time
- % episodes solved **without** `speedrun` (pure-Jev routing)
- regressions vs the three baselines: Kociemba-only (the ⚡ tool),
  Kociemba-only, and current Jev.

A policy change ships only if it beats the incumbent on the suite.
